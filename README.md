# 饮品热点雷达

把小红书上分散的饮品品牌内容和行业线索，整理成一份每周可筛选、可回看原帖的热点雷达。

[查看在线版](https://yajunmonk.github.io/beverage-hotspot-radar/) · [查看部署分支](https://github.com/YajunMonk/beverage-hotspot-radar/tree/main)

当前分支是公开工程源码，按“数据抓取 → 数据清洗 → 网页呈现”组织。它用于审阅方法、修改规则和运行公开网页；线上页面由 `main` 分支独立部署。

## 产品定位

饮品热点雷达服务于品牌、市场、内容和策略团队。它把一周内采集到的品牌官号内容，清洗为不重复的行业事件，再按主题、品牌和来源做成可浏览的网页，帮助使用者快速回答三个问题：

- 这一周，监测范围内发生了什么？
- 哪些是品牌已经发生的动作，哪些只是值得继续观察的线索？
- 如果要进一步判断，原始依据在哪里？

它不是全网热度排行榜，也不根据互动量推断销量或市场份额。每个事件和线索都尽量保留来源链接，方便回到原帖核对。

## 它能做什么

- **看行业事件**：把多条相似内容归并为一个事件，减少重复阅读。
- **按条件筛选**：支持主题、品牌和来源类型筛选，并保留热门标签。
- **区分事实和线索**：品牌官号内容进入本期事件统计；三方、KOC 和热点选题单独放在发现层。
- **回看原始证据**：事件卡片和内容便签可跳转至对应的小红书帖子或账号页面。
- **继续修改方法**：抓取、清洗、打标和网页呈现分别管理，修改规则时能找到明确入口。

## 核心工作流程

### 1. 数据抓取

先确定时间窗口并采集本期品牌官号内容；行业资讯、美食垂类和热点来源先进入来源池，实际取得的三方、KOC 和热点选题另放在发现层。当前以 Codex 辅助抓取为主，API 抓取位置已经预留。

这一阶段只负责保存原始事实和采集记录，不提前下行业结论。

[查看抓取方法](01_数据抓取/README.md)

### 2. 数据清洗

统一字段，去除重复内容，把多条相关帖子归并为事件，并补充主题、品牌、来源类型等标签。品牌官号事实层与三方 / KOC 发现层在这里分开统计。

筛选标准、主题定义和统计口径都写在规则文档里，后续可以直接修改和复核。

[查看清洗规则](02_数据清洗/README.md)

### 3. 网页呈现

把处理后的数据渲染成静态网页，提供筛选、标签、事件详情和原帖跳转。呈现层只负责展示，不重新定义业务口径。

[查看网页源码](03_网页呈现/README.md)

## 工程结构

完整本地项目按三个业务步骤组织；GitHub 公开源码沿用同一三步主结构。

| 目录 | 放什么 | 什么时候改 |
|---|---|---|
| [`01_数据抓取`](01_数据抓取/README.md) | 来源说明、抓取规则、API 占位 | 调整账号池、时间窗口或采集方式时 |
| [`02_数据清洗`](02_数据清洗/README.md) | 去重、主题、标签和统计规则 | 修改筛选标准、事件归并或打标时 |
| [`03_网页呈现`](03_网页呈现/README.md) | 脱敏数据、页面源码和使用说明 | 修改网页内容、样式或交互时 |
| `90_历史归档` | 冻结版本和历史材料 | 只在本地留存，不同步到公开仓库 |
| [`99_工程工具`](99_工程工具/README.md) | 构建与页面验收脚本 | 发布新版或检查页面时 |

## 怎么使用

如果只是查看结果，直接打开[在线版](https://yajunmonk.github.io/beverage-hotspot-radar/)。先看本周重点，再用主题、品牌或来源标签筛选；需要判断依据时，打开事件详情并回到原帖核对。

如果要修改项目，可以从对应步骤进入：

- 新增账号或调整抓取范围：进入 [`01_数据抓取`](01_数据抓取/README.md)；
- 修改主题、标签、去重或热点选题规则：进入 [`02_数据清洗`](02_数据清洗/README.md)；
- 修改页面样式、筛选交互或卡片信息：进入 [`03_网页呈现`](03_网页呈现/README.md)；
- 重新生成并验收公开页面：使用 [`99_工程工具`](99_工程工具/README.md)。

本地预览时，进入 `03_网页呈现/V1.1`，双击 `index.html` 即可查看。页面链接已移除临时访问参数；小红书原帖能否直接打开仍取决于平台登录状态。

## 公开范围

公开仓库包含方法文档、清洗规则、脱敏后的网页数据、页面源码和公开构建工具。原始抓取证据、内部运行记录、完整工作簿、临时访问参数和历史归档只保存在本地完整工程中。

因此，公开源码适合审阅方法、修改规则和运行页面；若要从头重建全部数据，需要配合本地原始输入。详细说明见[公开同步边界](PUBLICATION_BOUNDARY.md)。
