# 茶饮热点雷达：数据分析与 BI 执行规范 V1.2

> 状态：已确认执行｜生效版本：V1.2｜首个周期：2026-W30
> 目的：让抓取、清洗、打标、计算、分析和网页呈现每一步都有来源、有表格、有规则、有校验，任何接手者都能追溯并修改。

## 1. 产品定位

茶饮热点雷达是一套“可追溯的行业内容监测与判断辅助系统”。它帮助需求方回答四类问题：

1. 本周期有哪些品牌动作与具体事件？
2. 产品、联名、品牌事件分别有多大覆盖和互动表现？
3. 哪些品类、原料、IP、促销方式和热梗值得继续观察？
4. 每个结论由哪些原帖、规则和统计结果支持？

本产品提供决策证据，不把单品牌爆发、单条高赞或资讯号线索包装成行业趋势。

## 2. 三步工作流与文件边界

```text
01_数据抓取/
├── 来源名单/                         # 账号身份、来源层级、监测状态
├── Codex抓取/
│   ├── 原始数据/YYYY-Wxx/            # 原样保存，不覆盖历史
│   ├── 互动快照/YYYY-Wxx/            # 点赞、评论、收藏及抓取时间
│   └── 运行记录/YYYY-Wxx/            # 每次运行范围、成功/失败、异常
└── API抓取/                           # 预留，未接入前只保留说明

02_数据清洗/
├── 规则/
│   ├── 01_字段字典/
│   ├── 02_指标字典/
│   ├── 03_标签字典/
│   └── 04_分析策略与提示词/
├── 处理后数据/
│   ├── 主数据/                        # 长期维表；跨周期复用
│   └── Vx.x/周期快照/YYYY-Wxx/
│       ├── 01_标准化明细/
│       ├── 02_AI打标与人工复核/
│       ├── 03_汇总指标/
│       ├── 04_分析结论/
│       └── 05_BI数据集/
└── 校验记录/YYYY-Wxx/Vx.x/            # 质量报告、差异表、复核清单

03_网页呈现/
└── Vx.x/                              # 只读取已确认的 BI 数据集并渲染
```

边界原则：第一步保留证据，第二步产生口径、标签、指标与结论，第三步只展示和筛选，不在浏览器里重新计算业务指标。

## 3. 数据分层与来源使用规则

| 来源层 | 典型来源 | 可以做什么 | 不可以做什么 |
|---|---|---|---|
| 品牌事实层 | 品牌官方账号 | 进入正式事件、品牌动作和正式 KPI | 不能仅凭品牌自述判断行业趋势 |
| 行业发现层 | 媒体、资讯号、行业账号 | 发现活动、促销和行业线索，补充背景 | 不能与官方内容合并计算官方互动 KPI |
| KOC 体验层 | 测评号、美食号、消费者账号 | 观察体验、讨论和传播信号 | 不能替代品牌事实或销量证据 |
| 编辑选题层 | 热梗、营销观察账号 | 生成热点选题和借势提示 | 不进入行业品牌事件 KPI |

每条记录必须有 `source_class`。跨层展示可以并列，但跨层指标不得混算。数据质量检查中 `source_layer_contamination_count` 必须为 0。

## 4. 核心数据表

### 4.1 长期主数据

| 表名 | 一行代表什么 | 主键 | 主要用途 |
|---|---|---|---|
| `dim_brands` | 一个品牌 | `brand_id` | 品牌名称和状态统一 |
| `dim_accounts` | 一个被监测账号 | `account_id` | 账号身份、来源层级、监测状态 |
| `dim_entities` | 一个标准化实体 | `entity_id` | 原料、IP、人物、地点等实体统一 |
| `dim_tags` | 一个标签定义 | `tag_id` | 标签含义、边界、版本和审核要求 |
| `dim_metrics` | 一个指标定义 | `metric_id` | 口径、粒度、公式、适用范围 |

### 4.2 周期事实与关系表

| 表名 | 一行代表什么 | 主键/唯一键 | 备注 |
|---|---|---|---|
| `fact_contents` | 一篇标准化品牌内容 | `content_id` | 标题、正文、原帖、来源、品牌、时间 |
| `fact_engagement_snapshots` | 某篇内容的一次互动快照 | `observation_id` | 保留每次抓取，不覆盖旧值 |
| `fact_events` | 一个去重后的品牌事件 | `event_id` | 可关联多篇内容、多标签、多实体 |
| `bridge_event_content` | 一个事件与一篇内容的关联 | `event_id + content_id` | 防止按帖子重复计算事件 |
| `fact_tag_assignments` | 一个对象的一次标签判定 | `assignment_id` | 包含置信度、证据、审核状态 |
| `fact_source_signals` | 一条三方或 KOC 线索 | `signal_id` | 仅用于发现层与体验层 |
| `fact_promotion_offers` | 一条可核实促销信息 | `promotion_id` | 必须有活动机制、证据与有效期状态 |
| `tag_review_queue` | 一条待人工确认的标签任务 | `review_item_id` | 模型结果不能绕过此表直接进入正式 BI |

| `mart_tag_metrics` | 周期 × 标签 | 标签覆盖和互动分布、小样本状态 |
| `mart_brand_metrics` | 周期 × 品牌 | 事件数、内容数、互动分布、主题覆盖 |
| `mart_product_category` | 周期 × 产品品类 | 事件数、内容数、品牌数、互动分布 |
| `mart_ingredient` | 周期 × 原料/产品元素 | 事件数、内容数、品牌数、信号等级 |
| `mart_collaboration` | 周期 × 联名对象/领域 | IP 或品牌合作覆盖与互动分布 |
| `mart_promotion` | 周期 × 促销类型 | 经核实的活动数、品牌数、证据数 |
| `mart_hotspot` | 周期 × 热点选题 | 热梗原句、白话解释、热因、品牌借势角度、来源 |

## 5. 通用字段与可追溯要求

所有周期表按实际粒度尽量保留以下字段：

| 字段 | 说明 |
|---|---|
| `period_id` | 统计周期，如 `2026-W30` |
| `run_id` | 对应抓取/处理运行 |
| `source_url` | 可打开的证据原帖；公开版移除临时查询参数 |
| `captured_at` | 抓取或互动快照时间 |
| `rule_version` | 本行使用的规则版本 |
| `review_status` | `pending / approved / rejected / needs_review` |
| `reviewed_at` | 审核时间；未审核为空 |
| `evidence_note` | 标签或结论的简短证据 |

空值与零值必须区分：`0` 表示确认值为零；空值表示未采集、不可得或不适用。前端不得把空值显示为零。

## 6. 核心指标口径

### 6.1 主指标

| 指标 | 口径 | 展示规则 |
|---|---|---|
| 去重事件数 | 周期内唯一 `event_id` 数 | 主题可重叠，总览只展示去重数 |
| 品牌内容数 | 品牌事实层唯一 `content_id` 数 | 不混入三方和 KOC |
| 活跃品牌数 | 周期内至少有一条合格内容的品牌数 | 标明覆盖品牌范围 |
| 有效互动样本 N | 点赞为非负有效数值的内容数 | 与中位数、P75同时展示 |
| 点赞中位数 | 有效样本的 50% 分位数 | 核心互动指标 |
| 点赞 P75 | 有效样本的 75% 分位数 | 观察较高表现门槛 |
| 点赞均值 | 有效样本总点赞 ÷ N | 只作辅助，避免被单条爆款主导 |
| 点赞最大值 | 有效样本最大值 | 必须配合 N 与中位数阅读 |
| 人工复核完成率 | 已通过人工/Codex复核对象数 ÷ 应复核对象数 | 不代表数据真实性，只代表流程完成度 |

### 6.2 统计规则

- 分位数采用线性插值法；同一版本内不得临时更换算法。
- `N < 5` 标记为“小样本”，不得进入强弱排名，只能作为案例观察。
- 主题允许一件事同时属于产品动作、联名合作和品牌事件。必须同时展示“主题归属次数”和“去重事件数”。
- 当前只有一个完整可比周期，不计算周环比，不使用“持续增长”“上升趋势”等措辞。
- 至少有 2 个同口径周期后才展示环比；至少 4 个同口径周期后才允许输出趋势判断。

## 7. 标签体系与治理

正式标签分为十个维度：

1. 核心主题；
2. 业务动作；
3. 产品品类；
4. 原料/产品元素；
5. 联名领域/IP；
6. 促销机制；
7. 季节/场景；
8. 目标人群；
9. 内容形式；
10. 来源类型。

每个标签必须记录：标签 ID、名称、维度、父标签、定义、纳入条件、排除条件、正例、反例、适用对象粒度、适用来源层、单选/多选、判定规则或提示词、模型版本、置信度阈值、审核状态、版本、生效/失效日期和修改原因。

标签工作流：

```text
规则可直接判定 → approved
模型建议 → pending → 人工/Codex复核 → approved / rejected
低置信度、规则冲突、未知标签 → needs_review → 进入 tag_review_queue
```

只有 `approved` 标签进入 BI 统计。模型不能新增正式标签；未知标签必须先更新字典并留版本记录。

## 8. 分析流程与模型边界

```text
原始证据
  → 字段标准化与去重
  → 规则判定 + 模型A建议标签
  → 人工/Codex复核
  → 确定性脚本计算指标
  → 模型B基于指标表生成解释草稿
  → 人工确认结论
  → BI数据集
  → HTML网页与Excel工作簿
```

- 模型 A 只做语义识别与标签建议，不直接修改正式事实。
- 所有计数、分位数、排名、覆盖率和复核率由确定性脚本计算。
- 模型 B 只能引用输入表中的数值和案例 ID，不得编造销量、行业规模或未采集数据。
- 分析结论必须拆为 `conclusion`、`evidence_points`、`case_event_ids`、`boundary_note`、`review_status`。

## 9. 爆款与重点信号规则

V1.2 不把“绝对点赞数超过某值”永久定义为爆款。当前采用周期内相对阈值：

| 信号 | 暂行规则 | 用途 |
|---|---|---|
| 高互动内容 | 点赞 ≥ 同口径内容 P75 | 识别本周期上四分位内容 |
| 极高互动内容 | 点赞 ≥ P90 | 提醒检查是否由单条爆发主导 |
| 跨品牌信号 | 同一标签覆盖品牌数 ≥ 2 | 区分行业线索与单品牌案例 |
| 重点主题 | 事件数、品牌覆盖及互动分布综合观察 | 不使用单一分数替代判断 |
| 促销证据 | 明确机制 + 可打开原帖 + 已核实 | 仅标题命中关键词不算正式促销 |

阈值在积累至少 4 个同口径周期后复盘；在此之前标注为“暂行观察线”，不能包装为行业基准。

## 10. 促销信息规则

`fact_promotion_offers` 只收录正文、页面证据或经过核实的资讯内容中明确出现的活动机制。需记录：促销类型、优惠机制、适用产品、渠道、开始/结束时间（若可得）、来源层、原帖、证据文本、审核状态。

以下情况只进入候选复核，不进入正式促销统计：

- 数字或“券”字由无关语境误命中；
- 仅评论区提及，官方正文未确认；
- 没有可打开证据；
- 资讯号转述但尚未找到官方或独立核实依据。

## 11. 热点选题规则

每条热点必须单独填写：

- `hot_phrase`：热梗原句；
- `plain_explanation`：不懂梗的人也能看明白的解释；
- `why_now`：本期出现或被讨论的原因；
- `brand_application`：茶饮品牌可执行的借势方向；
- `source_url`、`published_at`、`captured_at`、互动快照；
- `boundary_note`：热梗热度不等于品牌转化效果。

热点只服务编辑选题，不进入品牌事实 KPI。

## 12. 数据质量与验收标准

每次发布前必须生成质量报告，至少检查：

| 检查项 | 目标 |
|---|---:|
| 主键重复 | 0 |
| 事件—内容孤儿关系 | 0 |
| 内容—实体孤儿关系 | 0 |
| 来源层混算 | 0 |
| 非法互动值 | 0 |
| 公开数据中的临时访问参数 | 0 |
| 指标与基础事实重算差异 | 0 |
| 页面核心数字与 BI 表差异 | 0 |
| 待复核项 | 必须显性展示，不要求强行清零 |
| 原帖可打开率 | 记录实测分母、分子和时间 |

验收顺序：表结构检查 → 主键/关系检查 → 指标重算对账 → Excel 公式错误扫描 → Excel 全表渲染检查 → 网页桌面/手机检查 → 原帖链接抽样回读 → 公开包隐私检查。

## 13. Excel、CSV、JSON 的关系

- CSV 是机器可读的单一事实来源，适合版本管理和 BI 导入。
- Excel 是管理与复核界面，必须由同一批 CSV/JSON 自动生成。
- JSON 是网页消费层，同样由同一批 BI 表自动生成。
- 三者不得分别手工维护。修改规则或数据后，重新运行构建和校验流程。

## 14. 版本与变更管理

- 历史周期和历史版本只读，不原地覆盖。
- 新增或修改字段、指标、标签、阈值时，先更新对应字典和本规范，再更新脚本。
- 每次构建写入 `manifest.json`：输入来源、文件校验值、规则版本、输出文件、生成时间、校验状态。
- 规则变化影响可比性时，必须在 `change_log` 中说明，并在页面标注“口径变化”。
- 本地完整数据可保留证据字段；公开版本必须移除临时访问参数、登录状态、私密身份信息和不适合公开的原始字段。

## 15. V1.2 当前限制

1. 当前正式品牌样本为已登记的 9 个品牌账号，不代表全行业。
2. 当前只有 2026-W30 一个完整对比周期，不能做可靠环比和趋势判断。
3. 三方和 KOC 数据用于发现与体验信号，不进入品牌正式 KPI。
4. 待复核事件和标签必须被显性列出；本期 39 个历史待复核项已逐条回读证据后处理为 35 条通过、4 条驳回，当前队列为 0，并非批量强制通过。
5. 促销模块只展示已核实证据，宁缺毋滥。

## 16. V1.2 完成定义

V1.2 只有同时满足以下条件才算完成：

- 文件夹、规范、字段字典、指标字典和标签字典齐全；
- 标准化明细、复核表、汇总指标、分析结论和 BI 数据集均已生成；
- 所有指标可由基础表重算，网页不再计算业务结果；
- Excel 可筛选、可复核、无公式错误，并通过全表视觉检查；
- 网页展示数据范围、质量状态、中位数/P75、分类指标、促销证据和热点解释；
- 旧有筛选、详情、搜索、原帖直达和移动端行为全部通过回归验收；
- 公开发布包不含临时访问参数或本地过程文件。
